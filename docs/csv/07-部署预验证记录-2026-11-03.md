## 演练中发现并已修正

1. **备份脚本依赖宿主机目录挂载**：在不共享宿主机目录的 Docker 环境（如未配置挂载的 Colima）里，挂载进去的脚本目录是空的，备份容器起不来。
   已改为把脚本打进备份服务自己的镜像（`deploy/backup/Dockerfile`）。
2. **数据库密码出现在命令行**：mysqldump / mysql 用 `-p密码` 会告警，且进程列表可见。已改为 `MYSQL_PWD` 环境变量。

## 注意事项

- HTTPS 叠加配置把证书和 nginx 配置以目录挂载方式放进前端容器（证书不应打进镜像）。在 macOS 的 Docker Desktop / Colima 上测试时，
  项目目录需要在虚拟机的共享目录里；Linux 服务器上没有这个问题。
- http → https 跳转按标准 443 端口生成地址；如果对外 HTTPS 用非标准端口，需要相应修改 `deploy/nginx/https.conf`。

### 查出的问题

**改密后令牌立即失效（已修）**：MySQL 的 `DATETIME` 把小数秒四舍五入，12:00:00.6 存成 12:00:01，而新令牌签发时间是 12:00:00，被当成改密前的旧令牌拒绝。大约一半的用户改完密码会被踢出；新账号首次登录都要改密，所以影响很大。这个问题是“改密后旧令牌失效”这项修改引入的，H2 的行为不同，自动化测试查不出来。改为改密时间截断到整秒。

### 演练暴露的流程缺口（已补）

- 配方只能一个成品一个成品地录，SKU 多时不可行：新增首版配方的 CSV 批量导入。
- 缺东西要到用时才发现：新增“上线检查”页面。

**局限**：演练的数据量很小，用的是接口和自动化浏览器，不是真人按培训材料操作。CSV 没有用真实 Excel 生成的文件试过（GBK 编码、日期格式等）。

### 并发（MySQL + HTTP）

之前实测过完工、取消、发料、收货、留样、出库、放行。这次补齐其余流程，每项同时发 8 个请求。

| 流程 | 结果 |
| --- | --- |
| 退货、退货处置、召回发起 / 通知 / 关闭、经销商审核和驳回、生码上限、电商推送 / 重试 / 取消、配方草稿和签批、备案完成、CAPA 完成和验证、偏差关闭 | 共 17 项，全部只生效一次，没有 500，没有死锁 |
| 之前的 8 项复测 | 全部通过 |

日志里的数据库报错只有同一平台单和配方版本号的唯一键冲突，是预期的兜底；配方草稿同时发起时后到的请求返回 409。

**查出的问题（已修）**

- **退货可以超过已发数量**：只发了 10 件，8 个请求同时各退 10 件全部成功，隔离区多出 80 件，库存凭空增加。现在同一客户的退货逐张办理（锁客户行）。
- **同一批次开出多个召回**：同时发起开出 8 张召回单，每张都逐客户生成通知。现在先锁批次再检查。
- **取消的电商单被改回失败**：重试因缺货失败、回滚后另开事务写“失败”，会盖掉这个间隙里成功的取消，之后这张单还能再重试出库。现在写之前重新锁并判断状态。

这三处的锁都放在事务第一句。MySQL 可重复读下，锁之前有过普通查询的话，拿到锁后仍读不到别人刚提交的数据，H2 测不出这一点，所以到 MySQL 上验证过。

**局限**：同一张表单连点两次造成的重复新增（如两张相同的调拨单）后端不判重，靠前端按钮的加载状态防止；网络层重试会产生重复。这类单据本身没有可判断的状态。

## 追溯和召回演练（2026-11-05）

搭一个答案已知的场景，核对系统查出来的流向，写成 `TraceRecallDrillTest`。

**场景**：原料 A1（0.6 kg，先到期）、A2（5 kg），一种工厂代采原料。MO1 产出 F1（用 A1 0.6 + A2 0.4），MO2 产出 F2（只用 A2），MO3 已发料未完工。F1 通过经销商发 40 给 C1、销售发 30 给 C2、电商发 5 给 C3；C2 退 10，转可售后再发给 C3。

### 准确的部分

| 检查 | 结果 |
| --- | --- |
| A1 查成品 | 只有 F1，正确排除 F2 |
| A1 查客户和数量 | C1 40、C2 30、C3 15，和答案一致 |
| A2 查成品 | F1、F2，并列出未完工的 MO3 |
| F1 查原料 | A1 0.6、A2 0.4、代采批号，用量一致 |
| 召回 F1 | 通知到 C1、C2、C3，批次冻结，继续出库时不会分配到 F1 |

### 查出的问题（已修）

- **问题原料做的成品还能放行**：原料冻结后，已发料的单子照样能完工并上市放行。放行时现在检查用料批次，有冻结或不合格的不能放行。
- **召回中可以解冻**：进行中的召回批次能被解冻，已召回的货又能发出去。现在要先关闭召回。
- **只有外部批号查不到**：供应商通报问题时只给得出他们的批号，追溯页直接报“不存在”，工厂代采的原料更是没有系统批次。现在查不到系统批号时按外部批号查，代采原料直接给出用了它的成品。
- **回收率到不了 100%**：回收进度按发出量算，上面的场景发出 85，但 10 件是普通退货后转卖的，实际在外 75。现在显示在外量。
- **期初批次不能召回**：系统里没有发货记录就提示“无需召回”，而期初批次上线前很可能已经发出去了。现在可以发起，并提示名单要到旧系统核对。
- **追溯结果留不下来**：没有报告可以存档。现在可以打印，打印时去掉导航和按钮，表格按纸宽收缩，批号不截断。

V10 迁移在已有数据的库上升级成功，查询用上了新索引。外部批号查询（3 种批号各查 5 次）最慢 38 毫秒，**但测试库只有 67 个批次**，没有测大数据量。并发 17 项复测通过，没有死锁。

### 局限

- **期初批次的召回名单靠线下**：系统提示了，但无法消除。上线时必须保留旧系统或台账（SOP-10 第 6 步）。

之前的空库演练主要靠接口。这次在全新的空库上（开启强制改密），只用页面操作，按岗位走完：管理员改密 → 建 6 个账号 → 建仓库 → 下载模板并导入物料、往来单位、配方 → 上线检查 → 采购下单收货 → 物料放行 → 委托单发料完工 → 上市放行 → 出库 → 按受托厂批号追溯 → 退货和报废 → 投诉 → 召回通知、回收、关闭。修复后在新的空库上重走了一遍。

主线没有走不通的地方。**查出的问题（已修）**：

- **新员工第一眼看到红色报错**：首次登录时页面照常加载，接口全部被“请先修改初始密码”拒绝，改密弹窗后面露着红色提示和错误块。现在改完密码才加载页面。
- **召回详情表头和数字反了**：表头写“已出 / 已回收”，数字是已回收在前，`0 / 30` 容易看成已出 0 件。
- **回收数字不一致**：进度条已按在外量算，旁边的数字、召回详情每行和总览待办还是发出量，同一个召回显示 0/30 和在外 25。都统一成在外量。
- **上线检查在空库上写“都已填写”**：一个物料都没有时显示“物料都已填写”“备案编号都已登记”，看着像已经检查通过。现在写“还没有物料，导入后再检查”。

**局限**：是脚本按岗位点页面，不是真人，能查出走不通和提示不对，查不出“好不好懂”，手册要请实际岗位的人试读。往来单位的“类别”只认全称（写“客户”会被拒绝并列出可填值），没有改。

### 修改

- **补货需求扣退货**：日均和预测历史都扣普通退货，否则退回的大单会抬高需求、多补货。**召回回收的不扣**：那批货确实卖掉了，是质量问题，不代表需求少了。这是判断，业务可以改。
- **控制字符**：JSON 请求里的文字统一去掉控制字符（保留制表符和换行）。**已经存进库的不会自动清理**。
- **依赖扫描**：`scripts/dep-scan.py` + 每周一次的 `dep-scan.yml`，发现未登记的漏洞时任务失败。判断过不影响的登记在 `scripts/dep-scan-allow.txt`。不放在 PR 检查里，免得外部服务不稳定或新公布漏洞时拦住无关的合并。

### 3 万批次复测

环境：Docker 上的 MySQL 8 + 后端，开发机，30 并发 20 秒。数据：30083 批次、10 万流水、2 万出库单、30 万审计，其中 3000 个待检、1800 个已过期的物料批次，总览待办 9770 条。

**第一次跑的数字作废**：灌数据的脚本中途报错，库里只有 83 个批次，P95 0.08 秒是假象。从结果里批次数不对发现的，修好脚本重跑。

| | P95 | 最慢 | 总览平均 | 错误 |
| --- | --- | --- | --- | --- |
| 修复前 | 2.36 秒 | 5.35 秒 | 2.14 秒 | 无 |
| 修复后 | 1.12 秒 | 3.99 秒 | 1.05 秒 | 无 |

**查出的问题（已修）**：上一轮新加的过期物料检查把几万个物料批次全读出来再过滤；总览没有缓存，几千条待办全塞进一个响应。现在过期物料用数据库条件查，临期成品先过滤再组装，总览每类最多显示 30 条，超出的合并成“还有 N 条”，总数和每日提醒不受影响。修复后单次打开总览 0.24 秒、21 KB。

**局限**：数据是构造的，待办 9770 条比真实情况极端，分布也比真实均匀。压测客户端和服务在同一台机器上。**这组数字不能和之前记录的 P95 0.96 秒直接比**，当时的数据分布不同。总览在 30 并发下平均 1.05 秒，仍是最慢的页面。

### 空库走查第一次上 CI（2026-11-06）

第一次超时：CI 比开发机慢 3 倍左右，“自有工厂”这步超过 60 秒，放宽到 180 秒。

第二次 13 步通过，第 14 步退货的成功提示没有出现。失败报告下载了 4 次都中断，**没有拿到 CI 上的页面快照，下面的原因是推断的**：

弹窗打开时取基础数据的第一个仓库作默认值。如果基础数据还没加载完，默认值就是空的，之后也不会补上。CI 慢，脚本点得比数据快；真实用户网络慢时一样，只是可以手动选。把仓库接口人为延迟 2.5 秒后：修复前显示“请选择”，修复后默认仓库正常。同样的写法共 6 处（退货登记、退货处置、经销商审核、采购收货、库存作业、销售出库），都改成打开前先等基础数据（`rd.ready()`）。

**局限**：基础数据很慢时，点按钮后要等加载完弹窗才出现，这段时间没有提示。
